## 3. The four divergences, fixed

Each of these is a place `PILOT.md` differs from settled core and did **not** list the difference in
its own cut table. All four are cheap now and expensive later.

### 3a. Restore clause (b) of the readiness predicate — core §5.2

PILOT's day-1 claim SQL says it is "copied out of core §5.3" and is not: the subtree-terminal check is
missing. Core §5.2 states exactly what that costs: *"`done` on a split card means I decomposed, not
the work is finished... Without (b), a gate becomes runnable while the subtree it is meant to check
has not been claimed."* With three tiers and dotted ids this is live — an epic-level dep satisfied by
a `done` story whose cards have not run.

The claim SQL to write into `harness/ledger/sql/claim.sql`, one statement, merging core §5.3 with
PILOT's two genuine improvements (`IS DISTINCT FROM` per ADR-0006, and `rank`):

```sql
WITH candidate AS (
  SELECT t.id FROM tasks t
   WHERE t.state = 'pending'
     AND t.attempts < t.max_attempts
     AND NOT EXISTS (SELECT 1 FROM unnest(t.deps) AS dep(id)
                      WHERE (SELECT state FROM tasks WHERE id = dep.id)
                            IS DISTINCT FROM 'done')          -- (a) ADR-0006
     AND NOT EXISTS (SELECT 1 FROM unnest(t.deps) AS dep(id)
                       JOIN tasks x ON x.id LIKE dep.id || '.%'
                      WHERE x.state NOT IN ('done','quarantined'))  -- (b) core §5.2
   ORDER BY t.priority DESC, t.rank ASC, t.id
   LIMIT 1 FOR UPDATE OF t SKIP LOCKED
)
UPDATE tasks
   SET state='leased', lease_holder=%s,
       lease_expires_at = now() + %s::interval,
       attempts = attempts + 1, updated_at = now()
  FROM candidate WHERE tasks.id = candidate.id
RETURNING tasks.*;
```

Note `attempts = attempts + 1` moves to **claim time**, not the reaper as PILOT day 2 has it. Core
§5.3's reason: *"This counts deliveries, which is what bounds a crash-looping card: a card whose
handler kills its worker never records an explicit failure."*

Keep PILOT's `rank` column — it is a real addition core lacks, and `working-agreement.md` is explicit
that `deps` constrains and `rank` decides and they must not be the same field.

### 3b. Add `runs`, `project`, `summary_schema_version` — core §12 step 1

Core §12: these three *"cannot be retrofitted. Half a day beyond the rest."* PILOT keeps `project`
and drops the other two without listing the cut. `runs` is what makes `intent_digest` — and therefore
the cross-run query core §4.2 calls the highest-value one — possible at all.

```sql
CREATE TABLE runs (
  root_id       text PRIMARY KEY REFERENCES tasks(id),
  project_id    text NOT NULL REFERENCES projects(id),   -- see §3f
  intent_digest text NOT NULL,     -- sha256 of the root intent text
  spec_digest   text,              -- sha256 of the frozen spec.md
  config_pin    jsonb NOT NULL,
  started_at    timestamptz NOT NULL DEFAULT now(),
  ended_at      timestamptz,
  outcome       text
);
```

Plus `summary_schema_version int NOT NULL DEFAULT 1` on `tasks`. The pilot need not *use* these
beyond writing them — the point is that the column exists so day-30 queries can reach back.

### 3f. `project` → `project_id`, with a `projects` table

Core §4.1 carries `project text NOT NULL, -- cross-run identity. NOT retrofittable.` and §12 sharpens
it: retrofitting `project` is *"effectively impossible, since old rows cannot be attributed."* That is
precisely the argument for spending the FK now — it is the one column that can never be corrected
later, so the cheapest moment to give it a home is before the first row exists.

There is already metadata waiting for the table: the repo path, the frozen `spec.md` digest, and the
`review_policy` defaults that `intake-and-review.md` §5 puts on the epic but which are really
project-level (`default: story`, `auto_accept_if`, `always_gate`).

**The id stays text, not a serial or uuid.** Core's ids are content-derived text throughout, and
every query in core §9.4 is written `where project = :p`. As `where project_id = 'todo-pilot'` that
stays legible at a psql prompt; as `where project_id = 7` it does not, and the lessons queries are
meant to be run by hand.

```sql
CREATE TABLE projects (
  id          text PRIMARY KEY,          -- 'todo-pilot'
  name        text NOT NULL,
  repo_path   text,
  spec_digest text,                      -- sha256 of the frozen spec.md, set day 4
  created_at  timestamptz NOT NULL DEFAULT now()
);
```

`tasks.project_id` and `runs.project_id` both `text NOT NULL REFERENCES projects(id)`. Index becomes
`tasks_project_idx ON tasks (project_id, created_at)`.

**This is a knowing divergence from core** and the sixth one, so it goes in CLAUDE.md's invariants
with the others. Consequence to carry: core §9.4's `queries/lessons.sql` and §9.3's tree query are
transcribed with `project` renamed to `project_id`, and `.claude/rules/sql.md` says transcribed SQL
and the design document are not allowed to drift — so the rename is recorded there as a deliberate
substitution rather than left to look like drift.

### 3c. Rename the `attempts` collision

PILOT has `attempts` as a column on the board table **and** as the name of a whole table. Core makes
it worse: the column is simultaneously the delivery counter and the fencing token. Three jobs, one
word.

- The **column** stays `attempts` (core's name, and it is the fencing token).
- The **table** becomes **`task_attempts`**, keyed `(task_id, n)`.

### 3d. Fix `kill`

Core §7's `kill` = quarantine, terminal. PILOT day 3's `kill` = requeue the story with your reason
attached. Opposite terminality on one verb, and it would land in the CLI on day 3.

Resolution — keep both behaviours, give each its own verb:

| Verb | Effect | Source |
|---|---|---|
| `hh reviews reject <story>` | requeues the story with the reason attached, exactly as a verify rejection does; round counter applies | PILOT day 3, `intake-and-review.md` §5 |
| `hh reviews kill <story>` | quarantined, terminal | core §7 |

`approve` unchanged. `edit`, `split` and `promote` (core §7's other three verbs) are **out for the
pilot** — `promote` in particular has no home because the pilot has no `notes` table. Record that in
README's known-absent list rather than leaving it silent.

### 3e. `tasks`, not `cards` — core §3.2

Core is unambiguous and already has a hook enforcing it: *"`task` and `card` are the same thing.
`task` in anything code-adjacent; *card* only in prose. Never `TaskCard`, never a `cards` table."*
`hooks/check_invariants.py` already carries `CREATE\s+TABLE\s+(IF\s+NOT\s+EXISTS\s+)?cards\b` as a
failure. So: the table is **`tasks`**, the prose says "card", and the existing hook stays as written.

PILOT's day-1 schema becomes, as one `schema.sql`:

```
projects(id, name, repo_path, spec_digest, created_at)
tasks(id, root_id, project_id, parent_id, tier, kind, title, contract, acceptance,
      deps[], touch[], produces[], consumes jsonb, non_goals, priority, rank,
      state, lease_holder, lease_expires_at, last_heartbeat_at, attempts,
      max_attempts, branch, outcome, summary_schema_version, created_at, updated_at)
task_attempts(task_id, n, kind, prompt, diff, rung_results jsonb, outcome, reason, started, ended)
runs(root_id, project_id, intent_digest, spec_digest, config_pin, started_at, ended_at, outcome)
reviews(story_id, opened, closed, verdict, reason)
questions(id, epic_id, asked_by_task, text, answer, answered_at)
```

`projects` is created first — `tasks` and `runs` both FK to it.

`tier` is `epic | story | card` — PILOT's meaning (hierarchy level), **not** core's (cost class).
This is a real, knowing divergence and it goes in CLAUDE.md's invariants as such, because if a worker
role ever filters on `tier` the claim query silently means something else. The pilot has one crude
prompt per kind and no model-selection axis, so nothing filters on it yet.

   *"if you find yourself opening a design document to check something, write the obvious thing and

3. **Pointer table** — `docs/harness-core-v3.md` §4–5 for the ledger, §6 for the workspace, §7 for

   for what a unit of work is.
4. **Invariants** — numbered, "these are not style preferences". Carry over from the kit's CLAUDE.md,

   carrying **both** predicate clauses; `attempts` on the row is the fencing token and
   `task_attempts` is the log; `reject` requeues and `kill` quarantines; `project_id` FKs to
   `projects`. Then a short **"knowing divergences from core"** subsection naming the two places the
   pilot's schema means something core does not — `tier` is hierarchy level here and cost class in
   core §3.1, and `project_id` replaces core's bare `project text` — so that a future session does
   not read one as a bug and "fix" it back.
5. **Principles that decide arguments** — six, from the kit: the predicate is the scheduler; cheapest
   mechanism wins; every mechanism costs whether or not it fires; **checks a card can fix are visible

   is a hook not a card; rule 62 (a mechanism with no detector is a mechanism you cannot know fired).
6. **Banned** — the class names (`Orchestrator`, `Coordinator`, `Manager`, `Controller`, `Router`,
   `Supervisor`), `TaskCard`, a `cards` table. Plus **do not call the prompts "jigs"** — PILOT is
   explicit, and `policy` §1.4 says a jig with no RED pass behind it is untested.
7. **What is deliberately absent in the pilot** — containers, per-attempt DB clone, model cache and
   `config_hash`, proper fencing, `preflight`, `spec_revision`, rung 3, notes/promote. So that a
   session does not helpfully add one back.
8. **Working style** — NOTES.md gets a bullet per surprise; the obvious thing beats the designed thing
   this week; if a mechanism never fires, that is a result, record it.

## 8. Verification

The scaffolding is done when all of these pass, run in the new directory:

**Hooks actually fire** — the kit's own test, adapted, and the reason `INSTALL.md` gives for it is
that a silently-failing hook is invisible:

```bash
echo '{"tool_input":{"file_path":"harness/ledger/claim.py","new_string":"x = datetime.now()"}}' \
  | python3 .claude/hooks/guard_invariants.py; echo "exit=$?"   # expect 2
echo '{"tool_input":{"file_path":"harness/worker/loop.py","new_string":"def run(): pass"}}' \
  | python3 .claude/hooks/guard_invariants.py; echo "exit=$?"   # expect 0
echo '{"tool_input":{"file_path":"docs/context/current-state.md","content":"# hand-edited"}}' \
  | python3 .claude/hooks/guard_invariants.py; echo "exit=$?"   # expect 2  ← the new block
```

**The banned-table hook fires** — this is the one that enforces §3e:

```bash
printf 'CREATE TABLE cards (id text);\n' > /tmp/bad.sql
python3 hooks/check_invariants.py /tmp/bad.sql; echo "exit=$?"   # expect 1
python3 hooks/check_invariants.py schema.sql;   echo "exit=$?"   # expect 0
```

**The schema loads, the FK holds, and the claim SQL parses against it:**

```bash
createdb hh_pilot && psql hh_pilot -f schema.sql
psql hh_pilot -c "INSERT INTO tasks(id, project_id, ...) VALUES ('t-x','nope',...)"  # expect FK violation
psql hh_pilot -c "PREPARE c(text,text) AS $(cat harness/ledger/sql/claim.sql | tr '\n' ' ')"
```

The `PREPARE` is the real check — it catches a column named in the predicate that the schema does not
have, which is exactly the class of error §3a's merge could introduce.

**Pre-commit installs and runs clean:** `pre-commit install && pre-commit run --all-files`.

**Claude Code sees the config:** `/context` lists `CLAUDE.md` and neither rules file (they are

PostToolUse; `/doctor` is clean. If a hook is missing and `/hooks` looks right,
